## Shared governance finding

The current published rule version is **2026-09-14.1**. GitHub and local DEVELOPMENT_PRINCIPLES.md share blob `999c12b8e30ebefdbff18c290ca64cbd8854c8a5`. The seven required shared files were read: principles, both templates, AGENTS, cloud guide, project catalog and cloud profiles.

Missing shared requirements include declared lifecycle classes; startup/shutdown/crash owners; canonical profile identity; cross-launcher daemon cardinality; attempt reconciliation before reconnect; readiness versus liveness; ownership-safe stale cleanup; disabled-startup semantics; reboot/logon/network/sleep recovery; lifecycle-preserving upgrades and uninstall; durable-job ownership beyond a frontend; and separate remote binding/catalog/call evidence. Keep project-catalog lightweight: link to lifecycle records after product owners validate them. Do not invent current compliance values or put runtime settings into cloud setup profiles. No universal daemon, service framework, database or autostart requirement is justified.

## Origin source finding and causal tree

Confirmed source defects at the current default HEAD:

1. `origin-agent/scripts/Run-ChatGPT-Tunnel.ps1:33–38` connects, performs one status request, and throws if not running/ready. It does not require healthy in that readiness condition.
2. Its catch at lines 53–59 sleeps and retries without stopping or reconciling an attempt-owned daemon/child. A successful spawn followed by failed connect/status/readiness can therefore reach a new connect without ownership reconciliation.
3. The outer finally releases the wrapper mutex but does not define child shutdown ownership. A wrapper mutex and Task Scheduler IgnoreNew constrain wrappers, not leaked tunnel children or independent launchers.
4. Packaging copies the runner and enable script from `origin-agent/scripts/build_release.py:125–136`. `Enable-ChatGPT-Tunnel-Startup.ps1` copies its adjacent runner into the installed cloud folder. `installation.py` preserves existing tunnel configuration; upgrading the engine alone does not prove wrapper migration.

The installed personal runner is byte-identical to source (SHA-256 `69b79dee46bc9c378f0bfc922037e4df8dddc0b7330de01da2dd9ab001b74cb7`). The installed school runner has a different profile/root/mutex and the same unsafe failure flow. No school generator was found by the repository search; its provenance and supported upgrade route must be established by the Origin owner. A local school customization is not yet a release-maintained source of truth.

Causal tree:

- **Confirmed mechanism:** connect may progress to a running daemon; a one-shot not-ready/status error enters catch; no cleanup precedes another connect.
- **Probable historical manifestation:** the recorded school failure at 14:06:37 UTC followed by recovery attempt 1 at 14:06:43 UTC is consistent with the reported two same-profile daemons. Historical daemon creation/parentage evidence is still needed to prove that specific chain; it was not reproduced in this audit.
- **Separate current failure:** no tunnel daemon was observed; four related startup tasks were Ready rather than Running, with last result `0xC000013A`. The process-termination source is not established. Fixing retry cleanup alone does not explain or close this failure.
- **Possible trigger:** logon before network/control-plane readiness. Tasks use logon triggers, IgnoreNew, three one-minute restarts, no execution time limit and no network condition. This is not evidence that scheduler Parallel mode caused duplication.
- **Independent host layer:** app installation/binding/catalog and real calls require fresh acceptance even after local recovery.
